# Password-login protection

This document specifies how Vigil protects credential verification against guessing, credential stuffing, and user enumeration, and the published guidance on which that design rests. It covers `PasswordLoginGuard`, `LoginPolicy`, and `LoginAttemptStore`, which also protect step-up PIN verification. Quoted text is reproduced from the cited page; the guidance was reviewed on 2026-10-03.

## Design rationale

- **Lockout vs throttling.** Neither source mandates lockout; ASVS requires documented controls and NIST caps consecutive failures at 100. A temporary, growing lock is a throttle: it bounds guesses without a permanent denial.
- **Duration and backoff.** Short first lock, doubling to a ceiling, forgetting failures after a quiet window (OWASP exponential lockout; Entra "one minute at first, and longer"; Okta auto-unlock).
- **Account vs IP.** Count per account (OWASP). IP counters alone fail against distributed attacks (OWASP credential stuffing); per-IP limits belong at the front door, and the account counter stays in the guard.
- **Lockout as denial of service.** An attacker who knows an identifier can lock it. Mitigate with short, capped locks, no permanent lock, a recovery path outside the password route, and (where the application can) a second signal such as known device, as Okta and Entra do. The guard only offers the first three; known-device logic is application policy.
- **Enumeration.** One rejection value for locked, unknown, inactive and wrong password; unknown identifiers are counted and locked like real ones so a lock does not reveal existence; unknown users still pay a full hash verification.
- **Timing vs CPU.** A locked identifier is rejected without lookup or hashing. That avoids letting lockouts become a CPU amplifier (Spring's cost warning). It means a locked identifier answers faster than an unlocked one, but because unknown identifiers lock identically, speed reveals only "this identifier was recently guessed", not "this account exists".
- **Multiple instances.** Node-local counters multiply the limit by the node count and are lost on restart. Entra and Okta keep this state in shared services. Vigil's default store is node-local; clusters implement `LoginAttemptStore` over shared storage with an atomic failure update.

## Specification

1. The application keeps the login route, the user lookup and the account status (see [system boundaries](../architecture/system-boundaries.md)). It passes a lookup function; the guard never reads a user store.
2. `PasswordLoginGuard.authenticate(identifier, password, lookup)` returns `LoginResult`: authenticated with a subject, or the single rejected value.
3. Key: normalized identifier (trimmed, `Locale.ROOT` lowercase) in the `password:` namespace. No IP key in the guard.
4. Policy (`LoginPolicy`): 5 failures, then 1 minute doubling to 15 minutes, failures forgotten after 15 quiet minutes, 100,000 tracked identifiers. Vigil builds it from `vigil.login.*` (`max-failures`, `base-lock`, `max-lock`, `failure-window`, `max-tracked-identifiers`) and exposes it, a default node-local `LoginAttemptStore`, and the `PasswordLoginGuard` as auto-configured beans that an application replaces by declaring its own.
5. One mechanism for every credential: step-up PIN verification (`StepUpAuthorizationService`) uses the same `LoginPolicy` and `LoginAttemptStore`, keyed per tenant and authorizing actor in the `step-up:` namespace. A PIN lock and a password lock are independent.
6. Success resets the counter; an inactive account with the right password is a failure, not a reset.
7. Rehash: `needsRehash` on success; the application persists the new hash.
8. Out of scope, for the application or front door: per-IP and global rate limits, CAPTCHA, MFA, lockout notification, recovery routes.

## Limitations
- **Concurrency.** Parallel requests can pass the lock check together, so up to `maxFailures - 1` plus the number of concurrent requests guesses precede the first lock.
- **Eviction.** A flood of distinct identifiers can evict counters from the bounded default store.
- **Timing floor.** Every verified attempt takes at least a floor calibrated from the encoder's own dummy verification, so stored hashes cheaper than the encoder's default (older work factors) are not faster than unknown users. The floor is a short wait per attempt, bounded by one dummy-verification time.
- **Stronger stored hashes.** A stored hash more expensive than the encoder's default cannot be hidden and remains distinguishable until it is rehashed or migrated. Keep stored hashes at or below the encoder's cost.
